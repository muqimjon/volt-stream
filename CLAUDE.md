# VoltStream

Kabel zavodi uchun hisob-kitob (savdo, ta'minot, to'lovlar, debitor/kreditor, ombor) dasturi.

## Arxitektura

`.NET 10` (LTS). Yechim uch qismdan iborat (`VoltStream.sln` + `src/web`):

**Backend** (`src/backend`) — Clean Architecture + CQRS:
- `VoltStream.Domain` — entitilar, enumlar.
- `VoltStream.Application` — CQRS komandalar/so'rovlar, interfeyslar, `Commons/Security` (ruxsatlar), `Commons/Mediator` (loyihaning o'z mediatori — `IRequest`/`IRequestHandler`/`IPipelineBehavior`, `AddMediator`), `Commons/Behaviors` (pipeline: `AuditLogBehavior` tashqarida, `PermissionBehavior` ichkarida — ro'yxatga olish tartibi shuni belgilaydi, buzma). Xaritalash — Mapster (`*MappingRegister : IRegister`).
- `VoltStream.Infrastructure` — EF Core (PostgreSQL/Npgsql), `AppDbContext`, JWT, Excel seeding (`ExcelDataSeeder`, `SeedData/*.xlsx` orqali), `DatabaseInitializer` (migratsiya + seeding fon `BackgroundService`).
- `VoltStream.WebApi` — controllerlar, middleware, Scalar API hujjati. Kompozitsiya `WebApiHostBuilder.Build` da; `Program.cs` shuni chaqiradi.

**Frontend** (`src/frontend`) — WPF (MVVM, CommunityToolkit.Mvvm, Mapster):
- `VoltStream.WPF` — oynalar/sahifalar/ViewModel'lar, DI uchun generic `Host`.
- `ApiServices` — Refit klient interfeyslari (`I*Api`) va modellar.

**Web** (`src/web/VoltStream.Web`) — Angular 22 + PWA (planshet/telefon uchun: savdo, kirim, sotilganlar, statistika, loglar, profil). Standalone komponentlar, signal'lar, UI kutubxonasiz. Build natijasi `src/backend/VoltStream.WebApi/wwwroot` ga tushadi (gitignored) va WebApi'ning o'zi SPA sifatida xizmat qiladi (`MapFallbackToFile`, `/api`, `/hubs`, `/scalar` bundan mustasno). `dotnet publish` `BuildWeb` target orqali `npm ci && npm run build` ni ishga tushiradi; oddiy Build esa `wwwroot/index.html` yo'q bo'lsa web'ni bir marta quradi (ikkalasi ham `-p:BuildWeb=false` bilan o'tkazib yuboriladi). Web kodi o'zgarsa `npm run build` yetarli — API'ni qayta ishga tushirish shart emas. Dev: `npm start` (proxy `/api`, `/hubs` → `https://localhost:7285`). Node 24 LTS (`.node-version`).

**Mobil** (`src/mobile/VoltStream.Mobile`) — .NET MAUI, faqat `net10.0-android`, **yupqa WebView qobiq**: APK ichida web YO'Q, web serverdan yuklanadi (Angular'ga tegilmaydi, web yangilanganda APK qayta tarqatilmaydi). Ikki sahifa: Ulanish (asosiy va zaxira manzil, `GET /api/health` tekshiruvi, `Preferences`) va Brauzer (to'liq ekran `WebView`; ochilganda avval asosiy, keyin zaxira manzil tekshiriladi — LAN `http://<ip>:5000` yoki tunnel `https://<domen>`; ikkalasi ham yo'q bo'lsa "Server topilmadi" ekrani). Sessiya WebView `localStorage` ida origin bo'yicha saqlanadi. `android:usesCleartextTraffic="true"` (LAN http uchun), JavaScript va DOM storage `WebViewHandler.Mapper` orqali yoqilgan. Matnlar `Texts.cs` da (faqat uz-Latn — qobiqda 12 ta satr, ichidagi web o'z tilini o'zi tanlaydi). Release imzosi: keystore `%APPDATA%\Ovoza\VoltStream\voltstream.keystore`, parol `VOLTSTREAM_KEYSTORE_PASS` env orqali (gitga tushmaydi) — `docs/DEPLOY.md`. `dotnet build VoltStream.sln` endi Android workload talab qiladi (Docker build faqat `VoltStream.WebApi.csproj` ni publish qiladi — ta'sir qilmaydi). Offline rejim yo'q (ataylab: talab qilinmagan).

## Ishga tushirish

1. PostgreSQL: `localhost:5432`, baza `voltstream`, `postgres/root` (`appsettings*.json` dagi `ConnectionStrings:DefaultConnection`).
2. Visual Studio: **"Combined"** launch profili (`VoltStream.slnLaunch`) — `VoltStream.WebApi` (https) + `VoltStream.WPF` ni birga ishga tushiradi. Bitta F5 yetarli.
3. CLI:
   ```
   dotnet build VoltStream.sln
   dotnet run --project src/backend/VoltStream.WebApi   # https://localhost:7285 + http://localhost:5123
   src/frontend/VoltStream.WPF/bin/Debug/net10.0-windows/VoltStream.WPF.exe
   ```

Testlar: `dotnet test tests/VoltStream.Application.Tests` (Docker kerak — haqiqiy `postgres:17-alpine` konteynerida migratsiyalar bilan). Buyruqlar real mediator va pipeline orqali yuboriladi; har test o'z `World` ini yaratadi (`db.NewWorld()`: 2 filial, 2 valyuta, xodimlar `Admin/Manager/Cashier/Seller/OtherSeller`). Pul o'zgarishlarini `LedgerAssert` bilan tekshir (Savdo sahifasi, hisobot va Kontragentlar qoldig'i teng). Pul, ombor yoki ruxsat mantiqiga tegsang — test qo'sh.

WebApi seeding'dan OLDIN tinglay boshlaydi (migratsiya/seeding `DatabaseInitializer` da fonda). Shuning uchun klient va server bir vaqtda ishga tushsa ham klient muzlab qolmaydi.

`Jwt:Secret` (kamida 32 belgi) MAJBURIY — yo'q bo'lsa server ishga tushmaydi. Dev qiymati `appsettings.Development.json` da (gitignored); production'da `appsettings.Production.json` (gitignored) yoki `Jwt__Secret` env. Kalit o'zgarsa barcha tokenlar bekor bo'ladi (WPF qayta login qiladi).

APK'ni release kaliti bilan imzolash uchun `VOLTSTREAM_KEYSTORE_PASS` env kerak (bo'lmasa skript ogohlantiradi va debug kaliti bilan imzolaydi — o'rnatilgan ilova ustidan yangilanmaydi). Server to'plamidagi image `docker load` bilan yuklanadi va `docker-compose.yml` dagi `image: voltstream-api:${VOLTSTREAM_VERSION:-latest}` uni qayta qurmasdan ishlatadi.

## Migratsiyalar

- `InitialMigration` (1.2.0 sxemasi, production `docs/upgrade-from-v1.sql` shunga moslangan) + keyingi o'zgarishlar alohida migratsiyalar bilan. Production bazalar bor — migratsiyalar faqat QO'SHILADI, qayta siqilmaydi. Yaratish (WebApi papkasidan): `ASPNETCORE_ENVIRONMENT=Development dotnet ef migrations add <Name> --project ../VoltStream.Infrastructure --startup-project . --output-dir Persistence/Migrations` (`dotnet-ef` 10.0.11 lokal manifestda).
- **Generatsiya fayllariga (migratsiya, snapshot) qo'l bilan tegilmaydi.** Kerakli natija model/konfiguratsiya orqali olinadi: default satr → `HasData`, ustun defaulti → `HasDefaultValue`.
- Ma'lumot backfill mexanizmi (`dataMigrations`, `__DataMigrationsHistory`) YO'Q — kerak emas: baza toza holatdan quriladi va `ExcelDataSeeder` foydalanuvchini `CreateUserCommand` orqali yaratgani uchun u darrov faol bo'ladi, filialga biriktiriladi va roliga qarab ruxsat oladi. `DatabaseInitializer` faqat migratsiya, default filial+ombor, omborsiz filiallarni omborga bog'lash (`LinkBranchWarehousesAsync`, idempotent) va indekslar bilan shug'ullanadi.
- Migratsiya fayliga qo'lda hech narsa yozilmaydi (`migrationBuilder.Sql` ham). Mavjud qatorlarga yangi FK kerak bo'lsa — bazada nullable + `DatabaseInitializer` da idempotent to'ldirish; mavjud jadvalga `HasData` qatori qo'shilmaydi (production'dagi Id bilan to'qnashadi).

## Yuk ro'yxatlari (SaleDraft)

- Ro'yxat — narxsiz savdo loyihasi: filial, ixtiyoriy mijoz, sana, izoh, qatorlar (mahsulot, rulon uzunligi, soni, jami metr; `composition` serverda). Ombor va mijoz qoldig'iga TA'SIR QILMAYDI, `Open` holatda erkin tahrirlanadi. Web/mobilda yaratiladi va chop etiladi; tasdiqlash hozircha FAQAT desktopda (Yuk ro'yxatlari sahifasi → savdo formasiga yuklanadi, tasdiqlovchi narx/chegirma/miqdorni o'zgartiradi).
- Tasdiq: `CreateSaleCommand.SaleDraftId` — handler `drafts.confirm` ni tekshiradi va savdo tranzaksiyasida shartli yangilash (`Open` → `Confirmed`, `ConfirmedSaleId`) bilan ro'yxatni egallaydi: bir ro'yxatdan aynan bitta savdo, savdo yiqilsa ro'yxat `Open` qoladi. Savdo tahrirlansa (Delete+Create) ro'yxat yangi savdoga bog'lanib `Confirmed` qoladi; savdo o'chirilsa ro'yxat yana `Open`. Tasdiqlangan/bekor qilingan ro'yxat ochiqlar ro'yxatida ko'rinmaydi (bazada qoladi); bekor qilinganda uning navbatdagi print job'lari ham bekor bo'ladi.
- Ruxsatlar: `drafts.manage` — o'z ro'yxatlari; `drafts.confirm` — filialdagi hamma ro'yxat (ko'rish, tahrir, bekor, tasdiq — tasdiq uchun `sales.create` ham); `reports.view` faqat KO'RISHni filialga kengaytiradi; `drafts.print` — ro'yxatni filial printeriga yuborish (`print.request` dan alohida). Ruxsat ro'yxat qulflanishidan OLDIN tekshiriladi (begona foydalanuvchiga holat bilinmasin); non-admin boshqa filial ro'yxatini tasdiqlasa 404.
- Ro'yxatda ishlatilgan mahsulot, kategoriya va mijoz o'chirilmaydi (FK Restrict + 409).

## Masofaviy chop etish (print-agent)

- `PrintJob` savdo YOKI ro'yxat uchun (`SaleId`/`SaleDraftId`, aynan bittasi — CHECK constraint). Ro'yxat chekini agent `GET /api/sale-drafts/{id}/receipt` dan oladi (savdo chek shakli, narxsiz, sarlavha "Yuk ro'yxati").
- Oqim: web/desktop `POST /api/print-jobs {saleId}` → `PrintJob` (Pending) → SignalR `PrintHub` (`/hubs/print`, JWT `access_token` query) `PrintJobCreated` filial agentlariga → agent (WPF `PrintAgentService`) `claim` (409 bo'lsa boshqa agent olgan) → `GET /api/sales/{id}/receipt` → `ReceiptDocumentBuilder` (Og'irlik rejimi) → printer → `complete`/`fail` → `PrintJobStatusChanged` so'rovchiga.
- Bir savdoga Pending/Printing job bo'lsa yangi so'rov 409 (`force` bilan qayta). `User.PrintPolicy` Auto/Ask/Deny: Deny → 403 serverda; Ask → agentda Ha/Yo'q dialog.
- `claim` shartli `UPDATE` (`Pending` → `Printing`) bilan atomik — bir job ikki agentga tegmaydi, yutqazgan agent 409 oladi.
- `fail` da urinish 3 tadan kam bo'lsa job navbatga qaytadi (`Pending`, `AgentUserId`/`ClaimedAt` tozalanadi, `Attempts` va oxirgi `Error` saqlanadi va agentlarga `PrintJobCreated` yuboriladi), 3-urinishdan keyin `Failed`. 3 daqiqadan ortiq `Printing` da osilib qolgan joblarni `PrintJobWatchdog` (Infrastructure, har 60 s) shu tarzda qaytaradi. `cancel` `Printing` jobni ham bekor qiladi (faqat so'rovchi yoki admin); bekor qilingan job qayta olinmaydi.
- Admin (`branches.all`) `POST /api/print-jobs` da `branchId` yuborib savdoni boshqa filial printeriga yo'naltirishi mumkin; non-admin uchun bu maydon e'tiborsiz (doim `sale.BranchId`). Web'da ko'p filialli foydalanuvchi "Chop etish" bosganda **qaysi filial printerida chop etilishi so'raladi** (`DialogService.choose`, savdo filiali oldindan tanlangan); bitta filialli hodimga so'ralmaydi — o'z filialining printerida chiqadi. Sabab: admin "Barcha filiallar" da turib bosganda job savdo filialiga tushib, o'sha filialda agent bo'lmasa navbatda jimgina qolib ketardi.
- Agent sozlamalari lokal: Sozlamalar → Printer (`settings.printer`), `%APPDATA%\Ovoza\VoltStream\printer.json`; ishlashi uchun `print.agent` ruxsati. Qayta ulanganda `GET /api/print-jobs/pending` bilan o'tkazib yuborilgan joblar chop etiladi.
- **Agent qaysi filialga xizmat qilishi — Printer tabidagi ANIQ sozlama** (`printer.json` dagi `branchId`), tokendan ham, header'dagi filial tanlagichidan ham OLINMAYDI. Sabab: admin boshqa filialni kuzatish uchun header'dan filial almashtirsa, o'sha filial cheklari uning printeridan chiqib ketmasligi kerak. Filial tanlanmagan bo'lsa agent ishga tushmaydi.
- Chek (`Receipt*`): og'irlik + miqdor bilan, narxsiz; desktop preview'da `sales.view_prices` bo'lsa Pul/Og'irlik toggle. Og'irlik rejimida "1 m og'irligi (kg)" va jami og'irlik ko'rsatiladi. Format A4 (`ReportService.BuildFixedDocument`) — termalga o'tkazilmaydi. Printer tabidagi Qog'oz (A4/A5) sozlamasi chop tiketiga (`PageMediaSize`) va chek sahifasi o'lchamiga qo'llanadi — printerning Windows'dagi standart qog'ozi (masalan A5) e'tiborga olinmaydi.
- **Rulon tarkibi:** chek mahsulot bo'yicha guruhlanadi (`GetSaleReceiptQuery`), har mahsulotga `Composition` — serverda `RollComposition` bilan hisoblangan, tilga bog'liq bo'lmagan matn (`2 × 50 + 1 × 70 + 1 × 100 + 1 × 30`). Asos: har `SaleItem` bitta uzunlik saqlaydi va kesilganda aynan bitta qoldiq bo'lak chiqadi (`HandleResidueAsync`), shuning uchun tarkib = `(RollCount − 1)` ta butun rulon + kesilgan bo'lak `TotalLength − (RollCount − 1) × LengthPerRoll` (3 xonagacha yaxlitlanadi). Klientlar (WPF chek, web Sotilganlar, mobil) uni QAYTA HISOBLAMAYDI — faqat ko'rsatadi. Guruhda uzunliklar aralash bo'lsa `LengthPerRoll = 0`, narxlar aralash bo'lsa `UnitPrice = null` (summa baribir to'g'ri). Sotuv tahlilida (`SaleItemHistoryQuery`) tarkib har qator uchun alohida. Tarkib KIRITILGAN qatorlarni aks ettiradi: 2018 m bitta qator qilib 400 lik guruhdan kiritilsa "5 × 400 + 1 × 18" chiqadi — bu xato emas; "3 × 400 + 1 × 370 + 1 × 448" uch qator qilib kiritilganda chiqadi.
- Og'irlik: `Product.IsWeightTracked` + `WeightPerUnit` (kg/birlik), `SaleItem.Weight` savdo paytida saqlanadi (keyin o'zgarmaydi). Kirim sahifasida og'irlik faqat YANGI mahsulot yaratilayotganda so'raladi (mavjud mahsulotning og'irligi o'zgarmaydi; xato kiritilsa Sozlamalar → Mahsulotlar dan to'g'rilanadi).
- **Job qaysi filialga boradi:** `PrintJob.BranchId` savdo qaysi filialda qilingan bo'lsa o'sha (so'rovchining tanlagan filiali emas). Admin `branches.all` bilan `branchId` ni ochiq ko'rsatib boshqa filial printeriga yubora oladi (preview'dagi "Filialga yuborish"). Preview'dagi "Chop etish" esa shu kompyuterdagi printerga chiqaradi.
- **Bir filialda bir nechta agent:** hammasi xabar oladi, lekin `claim` ni faqat bittasi yutadi (Pending→Printing shartli yangilash). Qaysi biri birinchi olishini `PrinterSettings.Priority` belgilaydi — agent claim'dan oldin `(Priority−1)×0,7s` kutadi. Job xato bersa yoki 3 daqiqa ichida tugamasa (watchdog) qayta Pending bo'ladi va navbatdagi qurilma oladi; 3 urinishdan keyin Failed.

## Klient ↔ server ulanishi

- Server manzili QO'LDA kiritiladi (host/port/https) va `%APPDATA%\Ovoza\VoltStream\connection.json` ga saqlanadi (`ApiConnectionStore`, faqat `Url`); eslab qolingan login/parol — `login.dat` (`CredentialStore`). Avto-kashf (discovery/broadcast/skan) va fon qayta-ulanish YO'Q.
- Bu ikki fayl ESKI desktop versiyaning `api-connection.json` / `credentials.dat` fayllaridan ATAYLAB alohida: mijoz kompyuterida eski va yangi ilova yonma-yon ishlaydi, umumiy nom bo'lsa biri ikkinchisining server manzili va loginini almashtirib yuborardi. Nomni eskisiga qaytarma. Formati bir xil zararsiz fayllar (`language.json`, `app-settings.json`, `namoz_times.json`) umumiy qoladi.
- WPF ishga tushganda login oynasini ko'rsatadi. Saqlangan URL bir marta tekshiriladi (`ServerHealth.IsAliveAsync` → `/api/health`); tirik bo'lsa va USB kalit/eslab qolingan parol bo'lsa avto-login.
- Login bosilganda URL bir marta tekshiriladi; ulanmasa `ConnectionRecovery` ulanish sozlamalari oynasini ochadi — foydalanuvchi qo'lda tuzatib davom etadi.
- Ish jarayonida biror API chaqiruvi serverga ulanolmasa (`AuthHeaderHandler`) o'sha sozlamalar oynasi ochiladi (bitta oyna, debounce).
- Portlar: dev `7285` (https), `5123` (http); native production `5000`.
- Internet: yagona manzil `https://volt-stream.muqimjon.uz` — Cloudflare named tunnel (`volt-stream-api`, mijoz serverida `cloudflared-volt-stream` xizmati) → API, web ham API'dan. Alohida web hosting (Cloudflare Pages) va alohida `api.` domeni ATAYLAB yo'q: web va API bitta image'da, versiya doim mos (sozlash — `docs/DEPLOY.md` §5).
- `/api/health` `[AllowAnonymous]` — ulanish tekshiruvi shu endpointga tayanadi.
- Avto-login: removable USB diskdagi `voltstream.key` (`DevKeyService`). Kalit bo'lmasa — qo'lda login.

## Biznes qoidalari (ATAYLAB shunday — buzma)

Bu yerdagi qoidalar "mantiqan g'alati" ko'rinishi mumkin, lekin BUYURTMACHI so'ragani uchun ataylab shunday qilingan. Upgrade/refactor paytida bularni "xato" deb tuzatma — avval shu ro'yxatni tekshir. Yangi shunday qaror qabul qilinsa, shu ro'yxatga qo'sh.

- **Ombor minusga tushishi mumkin (oversell) — standart holatda.** Mahsulot omborda yetarli bo'lmasa ham sotishga ruxsat beriladi; foydalanuvchi ogohlantiriladi va tasdiqlasa, savdo o'tadi va qoldiq minusga hisoblanadi. Buni butun tizim uchun BITTA sozlama boshqaradi: Sozlamalar → Umumiy, `AppSettings.AllowNegativeStock` (bitta qator, standart `true`, o'zgartirish `settings.general`). `false` bo'lsa `CreateSaleCommand` (demak tahrir va ro'yxat tasdig'i ham) qoldiq qatori manfiyga tushsa 409 beradi, klientlar esa mahsulot ro'yxatlarida faqat filial omborida bor narsani ko'rsatadi va ogohlantirish o'rniga rad etadi. `true` da tekshiruv YO'Q — uni majburiy qilib qo'yma.
- **Qoldiq optimistik konkurentlik bilan.** `WarehouseStock` Npgsql `xmin` (`Version`) bilan himoyalangan: bir qatorga parallel ikki amal tushsa biri 409 "Qoldiq boshqa amal bilan o'zgardi, qayta urinib ko'ring." oladi — yangilanish jimgina yo'qolmasligi uchun ataylab (server avtomatik qayta urinmaydi).
- **Rulonni kesish (partial roll).** So'ralgan metr to'plam uzunligiga bo'linmasa, foydalanuvchi tasdig'i bilan rulon kesiladi va qoldiq bo'lak alohida `WarehouseStock` sifatida omborga qaytadi (`HandleResidueAsync`).
- **Raqam kiritish universal.** Kasr ajratgich sifatida ham nuqta (`.`) ham vergul (`,`) qabul qilinadi — interfeys/OS tili qanday bo'lishidan qat'i nazar (`NumericInput.Normalize`). Buni bitta madaniyatga qulflab qo'yma.
- **To'lovda asosiy valyuta kursi qulf.** To'lov sahifasida tanlangan valyuta `IsDefault=true` bo'lsa, kurs maydoni tahrirlanmaydi.
- **IP-allowlist / so'rov-log middleware YO'Q.** Ilgari `ClientIpMiddleware` (IP oq ro'yxat) bor edi — u ulanishni bloklab, sekinlashtirgani uchun buyurtmachi talabi bilan butunlay olib tashlangan. Qaytarib kiritma.
- **Narxsiz savdo (web).** `sales.view_prices` bo'lmagan hodim savdo qilsa server narxni ombordagi `WarehouseStock.UnitPrice/DiscountRate` dan oladi va summani o'zi hisoblaydi; ofis keyin SaleEdit'da to'g'rilaydi. Bu "narx 0 bo'lib qoladi" xatosi emas.
- **Narxsiz kirim stock narxini buzmaydi.** `CreateSupplyCommand.UnitPrice` null bo'lsa mavjud stock narxi ustidan yozilmaydi (ilgari 0 yozib yuborardi).
- **Bir savdoga bitta faol print job.** Pending/Printing job bo'lsa yangi so'rov 409 — qog'oz isrofini oldini olish uchun ataylab. `force` faqat ongli qayta chop etish uchun.
- **Chekda narx yo'q (og'irlik + miqdor).** Mahsulot bir necha qo'ldan o'tadi, har qo'l o'z narxini qo'yadi — shuning uchun zavod cheki narxsiz. Desktopda faqat ruxsat bilan Pul rejimi.
- **Mijoz qoldig'i saqlanmaydi — operatsiyalar tarixidan hisoblanadi.** Qoldiq = `OpeningBalance + Σ CustomerOperations.Amount` (`AccountBalanceExtensions.FillBalancesAsync` — `AccountDto.Balance` qaytaradigan har so'rovda; `CustomerBalanceQuery`; hisobot ham shu formula). `Account.Balance` ustunini qaytarma va `account.Balance +=` yozma: saqlangan kesh 2026-06 da bir hisobda 46 221 000 ga buzilib, Savdo sahifasi bilan Mijoz hisoboti farq qilgan. `Account.Discount` va `Cash.Balance` hozircha saqlanadi.
- **Katalog umumiy, qoldiq ombor bo'yicha.** `Product` filialga bog'lanmaydi; `WarehouseStock` omborga bog'lanadi, filial qoldig'i = uning omboridagi qoldiq (omborni bo'lishgan filiallar bir xil qoldiqni ko'radi).
